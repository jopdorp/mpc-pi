# Raspberry Pi 5 boot configuration for the MPC2000XL appliance.
kernel=Image
arm_64bit=1
disable_overscan=1

# ===== AUDIO =====
# Onboard/HDMI audio is off. With the I2S overlay disabled below, the
# USB gadget is the only real sound device; the graph is clocked by a
# timer-driven null sink rather than by any hardware, so nothing depends
# on which card lands at index 0.
dtparam=audio=off
dtoverlay=vc4-kms-v3d,noaudio

# PCM5102A DAC plus PCM1808 ADC on the shared I2S bus. See
# overlays/mpc-audio-overlay.dts for the wiring this assumes.
#
# DISABLED until the converters are physically wired. The overlay
# creates the card unconditionally, and with nothing on the pins it is
# not merely useless - it is actively harmful:
#
#   * it PANICS THE KERNEL. Captured over netconsole:
#       dma dma2chan2: BUG: dma2chan2, IRQ with no descriptors
#       Unable to handle kernel paging request at deaddeaddeaddead
#       axi_desc_get / dw_axi_dma_set_hw_desc / snd_pcm_do_start
#       Kernel panic - not syncing: Oops: Fatal exception in interrupt
#     A use-after-free in the RP1 AXI DMA driver, reached by starting
#     the PCM - which is what every audio graph restart does. It is the
#     cause of the unexplained reboots this project spent days blaming
#     on power supplies and realtime tuning.
#   * it became the graph's clock by default, and its ~1ms DMA service
#     floor was then mistaken for a hardware limit on quantum 32.
#
# Disabling it in wireplumber was not enough: the ALSA device still
# exists and its DMA channel is still live. The card must not be created
# at all. Re-enable this line when converters are actually attached;
# nothing else about the audio configuration depends on it, because the
# instrument's output goes out over USB.
#
# WHEN THAT DAY COMES, three things from this investigation apply:
#
#   * The "~1ms DMA service floor" recorded elsewhere in this repo was
#     measured on THIS card with nothing wired to it, while its driver
#     was logging "IRQ with no descriptors" and heading for a panic. It
#     is not evidence about a real converter. Re-measure from scratch.
#   * The plan is an RP2040 as the clock source for the PCM1808 ADC,
#     which needs an external SCKI. That makes the Pi's I2S a slave to
#     that clock - so whatever generates it should clock BOTH converters,
#     or the board acquires two clock domains of its own on top of the
#     one it already reconciles with the USB host.
#   * I2S is structurally better suited to a small buffer than the USB
#     gadget is: one clock, one sample per LRCLK edge, no packetisation
#     and no two-clock reconciliation.
#
#     It also needs NO kernel patch. patches/kernel/0001 lifts
#     MIN_PERIODS in drivers/usb/gadget/function/u_audio.c, which is the
#     USB gadget's ALSA helper and is not in this path at all. I2S goes
#     through ASoC and soc-generic-dmaengine-pcm.c, which already sets
#     periods_min = 2 (line 123). Its real floor is
#     period_bytes_min = maxburst * 8, or 256 bytes when the DMA engine
#     reports no burst size - a genuine property of the hardware rather
#     than an arbitrary constant, which is what a limit should be.
#
#     The device-independent rule still holds: buffer = quantum means the
#     writer must be punctual forever, so 32 frames x 2 periods is the
#     honest target, not 1.
#dtoverlay=mpc-audio

# USB device mode on the USB-C connector (BCM2712's own DWC2 OTG at
# usb@480000, disabled in the base DTB). This is what lets the appliance
# present itself to a computer as a USB audio interface; the two type-A
# ports stay hosts on separate dwc3 controllers, so an external interface
# still works at the same time. Verified with fdtoverlay against the real
# bcm2712-rpi-5-b.dtb.
dtoverlay=dwc2,dr_mode=peripheral

# ===== BOOT TIME =====
# Radios the instrument never uses, and which cost real boot time:
# loading the wireless regulatory database took 1.59s and Bluetooth core
# init 0.81s, measured from dmesg timestamp gaps. The Maschine and the
# computer both arrive over USB; there is nothing to associate with.
dtoverlay=disable-wifi
dtoverlay=disable-bt

# ===== DISPLAY =====
# The panel LCD is delivered to external hardware over USB by the MK1 daemon,
# so no display is required in normal operation. HDMI stays available for
# bring-up and is harmless when nothing is attached.
display_auto_detect=1

# ===== SERIAL CONSOLE =====
enable_uart=1

# The Pi 5 sustains 2.4 GHz stock; raise only with real cooling and after
# re-running the throughput measurements, since the emulator is latency
# sensitive and thermal throttling shows up as audio dropouts.
# arm_freq=2800

# The Maschine MK1 is bus-powered, with 62 LEDs and two backlit screens.
# A Pi 5 caps TOTAL USB current at 600mA across all ports unless this is
# set, and 600mA is not obviously enough: driving every LED at full
# brightness once coincided with the controller falling off the bus
# entirely ("device descriptor read/64, error -110", then USB disconnect,
# recoverable only by unplugging).
#
# This raises the limit to 1.6A and REQUIRES a 5V/5A supply. With a
# smaller PSU the firmware refuses it, so it is safe to leave set - but
# an undervoltage event with it enabled means the supply, not the
# setting. Left commented until the supply is confirmed, because this
# project has misattributed symptoms to power twice already and should
# not do so again by guessing here.
#usb_max_current_enable=1
